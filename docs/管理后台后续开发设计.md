# 管理后台后续开发设计

> 2026-10-19实现更新：独立Java管理服务已位于`../server`，完成账号/预置角色/审计及知识版本审核发布闭环。本文保留长期规划；当前能力、接口、表和验证以[服务说明](../server/README.md)为准。管理网页和用户端内容只读分发已接通，模型包等仍待实现；最新验收见根docs/INTEGRATION.md。

2026-10-19 · 预留设计。管理端为独立程序，技术版本在真正开发前核验；不受小程序当前缺少管理UI而跳过审核流程。

## 范围和优先级

| 模块 | 管理动作 | 边界 |
|---|---|---|
| 内容管理 | 编辑知识双表达、引用、版本、提交审核、下架 | 专业/白话同版本语义一致，未审核不发布 |
| 模型/参考数据 | 导入受限schema、录入适用范围/原文位置/单位、挂接核验向量 | 不远程执行自由公式；开发工程测试不等于临床批准 |
| 审核发布 | 审核、批准、拒绝、发布、撤回、包版本回滚 | 编写人不能批准自己的版本；批准记录与散列固化 |
| 反馈工单 | 分派、状态流转、真实回复、附件权限 | 不默认查看用户所有健康档案；联系方式用途受限 |
| 服务运维 | 任务状态、失败重试、供应商状态、清理失败告警 | 不在界面显示令牌、原始报告或完整健康请求体 |
| 删除/导出监管 | 查看逐域进度、失败原因、受控重试 | 不把“已接收”写成“已删除”；审计不得保留原始健康副本 |
| 管理账号/审计 | 角色、最小权限、操作事件、会话撤销 | 与小程序微信用户身份和token隔离 |

暂不提供医生聊天、诊断、处方、支付、医院系统对接或运营批量浏览健康数据。

## 建议角色和权限

content_editor负责草稿；clinical_reviewer负责模型/医学内容核验；publisher执行批准版本发布；support_agent处理授权范围内的工单；ops查看任务和基础设施；security_admin维护管理账号/权限。

每个接口以权限码鉴权，例如content:edit、model:review、bundle:publish、feedback:reply、deletion:retry、audit:read。页面隐藏按钮不是访问控制。审核/发布二人分离；正式角色名单、人员资质和审批责任需业务确认。

管理账号的登录渠道、MFA、会话期限后续独立确定，不能直接复用小程序wx-login。管理JWT使用独立密钥/issuer/audience；用户端已固定audience=miniapp，不能用管理token访问用户资源。部署使用独立服务名、端口和入口白名单。

## 页面与API草案

| 页面 | API命名空间（建议） | 主要行为 |
|---|---|---|
| 内容列表/编辑/版本 | /admin/api/v1/knowledge | 查草稿、创建版本、提交审核 |
| 模型登记/证据/核验 | /admin/api/v1/models | 编辑元数据、登记函数ID与受限参数、录入证据 |
| 审核工作台 | /admin/api/v1/reviews | 独立审批、意见与责任人留痕 |
| 发布/回滚 | /admin/api/v1/releases | 组包、校验散列、发布指针切换 |
| 反馈列表/详情 | /admin/api/v1/feedback | 授权范围内工单、回复与附件访问 |
| 任务中心 | /admin/api/v1/jobs | 状态、重试、取消；外部动作前复查授权 |
| 数据删除进度 | /admin/api/v1/deletions | 逐域状态，受控重试和审计 |
| 账号/权限/审计 | /admin/api/v1/operators、roles、audits | 角色隔离与最小可见信息 |

具体请求/响应、分页、If-Match和UUID幂等必须在实施前形成独立OpenAPI。管理写操作不能直改生产阈值；发布调用受控领域命令或独立发布产物，用户服务只消费批准的不可变版本。

## 状态流和数据边界

参考/内容版本建议采用draft → submitted → reviewed → approved → published；拒绝回到新草稿，已发布版本不就地修改，修订产生新版本。撤回后阻断新的参考使用并提示历史关联，不能篡改用户历史快照。发布与回滚必须校验引擎兼容性、审核证据和包完整性。

管理自身表建议为admin_operator、admin_role、admin_permission、operator_role、role_permission、admin_session、admin_audit_event。内容、模型和审核表参照用户后端设计。是否共库必须在开发前确定；即使共库，也为两端使用不同数据库账号和最小表权限，不采用两个服务自由写同一领域表的方式。

临时报告、工单附件、删除对象使用私有短时授权。没有额外审批时普通运营只见工单必要信息，不能用列表/搜索/导出绕过健康数据隔离。审计记录动作、资源、责任人、结果和requestId，禁止保存健康全文、token和生日。

## 开发前置与验收

需确认管理用户名单、身份来源和MFA、技术栈、网络边界、共库/跨服务方式、临床审核责任、内容授权证据、数据保留期限及发布SOP。

验收至少包含：权限矩阵越权、同人自审拦截、过期草稿版本冲突、重复发布幂等、撤回/回滚、未批准内容无法被用户服务读取、任务重试不重复外发、操作日志脱敏、账号撤销即时生效。真实管理应用实现时补UI设计和可访问性验收，本轮不创建空壳管理登录页。
