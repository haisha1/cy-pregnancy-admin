# 表结构与事务设计

实际DDL为`src/main/resources/db/migration/V1__admin_accounts_and_knowledge.sql`。独立数据库`cy_pregnancy_admin`，没有用户端健康档案表或跨库访问。数据库内部主键BIGINT，对外资源使用小写UUID v4，业务版本revision与内容version_no分开。

## 账号和访问控制

| 表 | 字段要点 | 约束 |
|---|---|---|
| admin_operator | client_uuid、username、password_hash、display_name、state、revision、created_at | UUID/用户名分别唯一；用户名小写ASCII；密码仅BCrypt；state=active/disabled由应用校验 |
| admin_role | code、name | 预置四种角色，只读清单 |
| admin_role_permission | role_code、permission_code | 组合主键，role_code外键；权限字符串与代码注解一致 |
| admin_operator_role | operator_id、role_code | 组合主键及两侧外键 |
| admin_session | client_uuid、operator_id、expires_at、revoked_at、created_at | session UUID唯一，operator_id外键及查询索引 |

首次账号初始化只在启用bootstrap且表为空时执行，角色为security_admin；重启不覆盖已有账号。账号状态/角色/密码变化递增revision、撤销全部会话；角色和状态查询来自数据库，不能信任客户端或JWT附加角色。

当前精简RBAC使用预置role_permission目录，未单独实现可编辑admin_permission表及任意权限管理UI；未来扩展需写新迁移和权限矩阵测试。安全管理员不自动拥有knowledge权限。

## 知识版本

| 表 | 字段要点 | 约束 |
|---|---|---|
| admin_knowledge_article | client_uuid、slug、published_version_id、revision、created_at | UUID/slug唯一；发布指针可空，FK到版本 |
| admin_knowledge_version | client_uuid、article_id、version_no、title、category、pro_content、plain_content、references_json、evidence_note | UUID唯一，(article_id,version_no)唯一；双表达同版 |
| 同一版本的状态字段 | state、author_id、reviewer_id、review_note、publisher_id、published_at、revision | 作者/审核者/发布者外键，允许后两者在尚未审核/发布时为空 |

可编辑状态仅draft；submitted → approved/rejected；approved → published；当前published可withdrawn。拒绝/发布/下架后需新建draft版本，旧正文不覆盖。每个条目可有多个待处理版本，但只有一个发布指针；发布更新指针，旧published版本仍作为历史保留，currentlyPublished从指针派生，不能只看state判断当前。

新版本插入会递增article.revision；编辑/送审/审核递增version.revision；发布递增两者；下架递增两者并显式NULL指针。单纯新增草稿不改变已发布指针。跨表指针的同条目归属由Service检查，不能靠一个版本ID的外键证明。

引用目前登记为字符串数组，医学来源、许可和证据由人审核；尚未实现独立文献/模型注册和受控参考包。内容正文存MEDIUMTEXT，API仍限制每种表达最多20000字符，禁止借底层列类型绕过输入限制。

## 幂等和审计

| 表 | 内容与规则 |
|---|---|
| admin_write_lock | 固定id=1；FOR UPDATE为低流量管理写入建立跨实例串行窗口 |
| admin_idempotency | actor_id+command_scope+operation_uuid唯一；payload_hash为规范化载荷的HMAC；response_json仅最小回执 |
| admin_audit_event | actor_id、resource_type/uuid、action、result_code、request_id、occurred_at；无请求体、密码和正文 |

管理命令整体在一个TransactionTemplate事务中：写锁 → 当前会话/权限复核 → 幂等比较 → 资源版本/状态检查 → 业务更新 → 审计 → 回执。任何异常回滚整个事务，测试注入审计失败验证不会留下半个条目或残留回执。

登录使用独立事务创建会话并写登录事件，失败登录记录最小失败事件；退出事务撤销会话并审计。当前没有为所有403/校验失败统一建持久化安全审计，也没有审计删除API，后续监控设计需补失败访问采集策略。

幂等HMAC目前使用管理端密钥，密钥轮换会影响历史载荷比较；正式生产前需设计独立稳定用途密钥/版本迁移与回执保留期，不能直接删除记录后让旧操作重放。首次发行阶段保留已成功回执，不自动清理。会话、审计、幂等及内容的正式保留周期尚待制定。

## 数据库变更规则

V1执行后不再改写，后续增加V2/V3。不要运行Flyway clean，不把含未知表的库强制baseline。管理数据库使用独立云端账号；若未来与用户端交换发布内容，通过明确发布产物或服务协议，不能让两个服务任意写对方领域表。
